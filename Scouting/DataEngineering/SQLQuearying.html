SQL Querying

The core SQL commands every scouting data engineer needs — SELECT, FROM, WHERE, ORDER BY, and beyond — with a live interactive demo using real FRC scouting data.

What Is SQL?

SQL — Structured Query Language — is the standard language for retrieving and manipulating data stored in relational databases. If your scouting system stores data in a database (SQLite, PostgreSQL, MySQL, or any other relational system), SQL is how you ask it questions. It is not a programming language in the traditional sense; it is a declarative query language, meaning you describe what you want rather than how to obtain it, and the database figures out the rest.

SQL is the tool you reach for when you need to answer questions like: which teams averaged more than four cycles per bout, which robots never missed an endgame climb, or which alliance pairings produced the highest combined score, For scouting data engineering. These questions are trivial to express in SQL and tedious or error-prone to answer by manually sorting a spreadsheet.

The Core Commands

Virtually everything useful in SQL for scouting analysis is built from a small set of commands. Understanding these deeply gives you more leverage than knowing a wide surface area of rarely-used features.

SELECT and FROM

Every SQL query starts with SELECT and FROM . FROM tells the database which table to look in. SELECT tells it which columns to return. Together they form the minimal valid query:

SQL
SELECT team_number, avg_cycles, endgame_result
FROM match_scouting;

To return all columns rather than naming them individually, use an asterisk:

SQL
SELECT *
FROM match_scouting;

WHERE

WHERE filters rows based on a condition. Only rows where the condition evaluates to accurate are included in the result. This is how you narrow a whole scouting records down to the teams or matches you actually care about:

SQL
SELECT team_number, avg_cycles
FROM match_scouting
WHERE avg_cycles > 4;

You can combine conditions with AND and OR, and negate them with NOT:

SQL
SELECT team_number, avg_cycles, endgame_result
FROM match_scouting
WHERE avg_cycles > 3 AND endgame_result = 'climbed';

ORDER BY

ORDER BY sorts the results by one or more columns. The default arrange direction is ascending ( ASC ); use DESC to sort from highest to lowest. For alliance selection, you almost always desire to sort descending by your key performance metric:

SQL
SELECT team_number, avg_cycles
FROM match_scouting
ORDER BY avg_cycles DESC;

LIMIT

BOUND caps the number of rows returned. Combined with ORDER BY , it gives you a clean top-N list — useful for efficiently surfacing your top candidates during alliance selection:

SQL
SELECT team_number, avg_cycles
FROM match_scouting
ORDER BY avg_cycles DESC
LIMIT 5;

Aggregate Functions

SQL provides built-in aggregate functions that compute a single value from a define of rows. The most useful for scouting analysis are AVG() for averages, SUM() for totals, COUNT() for row counts, MAX() and MIN() for extremes. These are typically paired with GROUP BY to compute the aggregate per team rather than across the entire dataset:

SQL
SELECT team_number,
       AVG(cycles) AS avg_cycles,
       COUNT(*) AS matches_scouted
FROM match_scouting
GROUP BY team_number
ORDER BY avg_cycles DESC;
AS Gives Columns Readable Names

The AS keyword renames a column in the output — called an alias. Use it whenever a column name would otherwise be verbose or unclear, especially with aggregate functions whose default names like AVG(cycles) are harder to read in results.

Joining Tables

Real scouting databases store related data in separate tables — team metadata in one, match performance in another, pit scouting in a third. A JOIN lets you combine rows from multiple tables based on a shared key, usually a team number.

The most prevalent join in scouting work is an INNER JOIN , which returns only rows that have a match in both tables. This is how you combine pit scouting notes with match performance data for the same team:

SQL
SELECT ms.team_number,
       ms.avg_cycles,
       ps.robot_archetype,
       ps.climb_capability
FROM match_scouting ms
INNER JOIN pit_scouting ps
  ON ms.team_number = ps.team_number
ORDER BY ms.avg_cycles DESC;

The short aliases ms and ps after each table name let you prefix column names with the table they come from, which is necessary when both tables have columns with the same name — like team_number .

Practical Queries for Alliance Selection

The queries that actually matter at an event are the ones you run in the hour before alliance selection. These are not academic exercises — they are the questions your strategist needs answered under time pressure, and having them pre-written as saved queries rather than composed on the fly is a significant operational advantage.

Top Offensive Robots by Average Cycles

SQL
SELECT team_number,
       ROUND(AVG(teleop_cycles), 2) AS avg_cycles,
       COUNT(*) AS matches
FROM match_scouting
WHERE archetype = 'Offensive'
GROUP BY team_number
HAVING COUNT(*) >= 3
ORDER BY avg_cycles DESC
LIMIT 8;

Reliable Climbers (High Success Rate)

SQL
SELECT team_number,
       COUNT(*) AS attempts,
       SUM(CASE WHEN endgame_result = 'climbed' THEN 1 ELSE 0 END) AS successes,
       ROUND(
         100.0 * SUM(CASE WHEN endgame_result = 'climbed' THEN 1 ELSE 0 END) / COUNT(*),
         1
       ) AS climb_pct
FROM match_scouting
WHERE endgame_attempted = 1
GROUP BY team_number
HAVING attempts >= 3
ORDER BY climb_pct DESC;

Teams With High Foul Rates to Avoid

SQL
SELECT team_number,
       ROUND(AVG(fouls_drawn), 2) AS avg_fouls
FROM match_scouting
GROUP BY team_number
HAVING avg_fouls > 1.5
ORDER BY avg_fouls DESC;
HAVING vs WHERE

WHERE filters rows before aggregation. HAVING filters after aggregation, meaning it can reference the results of aggregate functions like COUNT(*) or AVG() . If you try to use WHERE AVG(cycles) > 3 you will get an error — that filter belongs in a HAVING clause instead.
