Data Standardization

Six scouts watching the same robot in the same match can produce six different numbers. Standardization is the set of agreements, formats, and practices that make their data add up — and keep it adding up when new scouts join, new datasets arrive, or the season changes.

Two Kinds of Standardization

When scouting programs talk about standardization problems, they usually mean one of two very different things, and solving one does not solve the other. The first is observational standardization — a miss, a successful climb, making sure that every scout applies the same definition of what counts as a cycle, or a foul. The second is structural standardization — making sure that all the data from all scouts arrives in the same format, with the same column names, the identical value encodings, and the same units, so that it can be merged and analyzed without transformation errors.

Both matter. A scouting records where every scout agrees on what a "miss" means but half of them record it as 0 and the other half as false is not usable without a cleanup pass. A dataset where every scout uses the same schema but some count a deflected shot as a miss and others count it as a score is not accurate regardless of how clean the format is. A standardized scouting program gets both appropriate, and it gets them right before the event — not as a post-hoc fix to a messy export.

Observational Standardization

The root cause of most observational inconsistency is that scouts are given field names on a form without definitions. The form says "Missed Shots" and the scout fills in a number — but the form never specified whether a shot that bounced off the target and was recovered counts as a miss, whether a shot attempted but blocked by a defender counts, or whether a shot that the scout wasn't tracking when it happened should be left out or estimated. Two scouts, both filling in the same field in good faith, will arrive at unique answers because they made different assumptions about those edge cases.

Writing Field Definitions That Actually Work

A good field definition is short enough to memorize but precise enough to resolve every realistic edge case. It specifies the trigger event — the exact moment that separates "before" from "after" for purposes of counting — and explicitly handles the most common ambiguous situations. For a cycle count, the definition might read: "Count one cycle each time the robot releases a game piece into a scoring position. Count a release that occurs outside the scoring zone as a miss, not a cycle. Count a release during defense contact the same as any other — not how it got there.", what matters is where the piece landed

The effort of writing these definitions pays for itself many times over across a season. Scouts who have clear definitions create faster decisions in the moment — they don't pause to feel about whether this situation counts. And when two scouts' numbers disagree, a clear definition gives you a reference to adjudicate the dispute. Without it, every inconsistency becomes a debate about intent.

The Calibration Problem

Writing definitions is necessary but not sufficient. Scouts also need to apply them correctly, which means they depend on practice applying them to real situations before the stakes are live. A pre-event calibration session — described in Scout Training Protocols — is the mechanism for this, but calibration only works if it uses scenarios specific enough to surface the actual edge cases your definitions need to resolve. A generic "here's what a game piece run looks like" demonstration is not calibration. A session where scouts watch video of contested situations, record their individual judgments, and then compare and consider differences is calibration.

Agreement Is Not the Same as Accuracy

A calibration session where all six scouts arrive at the uniform answer is good — but only if that answer is the correct one. It's possible for an entire team to converge on the wrong interpretation of a field, producing internally consistent data that is consistently wrong. Cross-reference your definitions against the game manual and against match score records to verify that your scouts' counts, when added up, reflect what the official scoreboard shows. Consensus without validation is not standardization — it is coordinated error.

Structural Standardization

Structural standardization is about the shape of the data — what fields exist, what they are called, what types of values they contain, and how those values are encoded. Every scout on your team should be producing data that looks identical in structure, whether from a new scout device — or an imported CSV from a paper, fill-season form update, scouting back-and every new dataset that enters your system-a mid — should conform to the same schema before it touches your analysis layer.

Defining Your Schema

A schema is a formal description of your match data: the name of every column, its allowed values, its data type, and whether it is required or optional. Defining your schema explicitly — even in a uncomplicated spreadsheet — forces you to make decisions that would otherwise be left to individual scouts' intuition. The schema is the contract that every data source must fulfill.

Here is an example of what a schema definition looks like for a small define of scouting fields:

Field Name Type Allowed Values Required Notes
match_number INT 1 – 200 ✅ Yes Qualification match number
robot_number INT 1 – 9999 ✅ Yes No leading zeros, no "Team " prefix
auto_cycles INT 0 – 6 ✅ Yes Successful scores in auto period only
teleop_cycles INT 0 – 20 ✅ Yes Successful scores in teleop period only
missed_shots INT 0 – 20 ✅ Yes Attempts that did not score; see field definition
endgame ENUM none, park, docked, engaged ✅ Yes Final state at buzzer, not attempted state
defended BOOL true / false ✅ Yes Was robot under significant defense this match?
defense_rating ENUM none, light, heavy ✅ Yes Defense this robot played, not received
notes STR Free text ❌ No Optional qualitative observations
scout_id STR Free text ✅ Yes Consistent scout identifier for cross-scout analysis

Enforcing the Schema at Collection Time

A schema definition is only useful if it is enforced. If your scouting app allows scouts to submit a robot number as "Team 2468" or an endgame value as "Climbed" rather than the defined enum option, the schema has failed as a constraint. Every field with a defined type or allowed value set should be enforced by the collection tool itself — dropdowns for enums, numeric keyboards for integers, challenging input limits for range constraints. Scouts should not be able to produce non-conforming data in normal operation.

For paper-hoc transcription-based collection with post, enforcement happens at the transcription step rather than the collection step. The transcription template should have data validation rules applied at the spreadsheet level — choice menu lists for categorical fields, integer-only cells for count fields, and a conditional formatting flag that highlights any cell where the entered value falls outside the allowed range.

Merging New Data Into an Existing Dataset

At some point during an event, your dataset will need to absorb data that didn't originate from your primary collection system. A back-filled paper form that was transcribed separately. A CSV exported from a partner team's scouting app. Data from a different event that you want to use as a pre-event baseline. In each of these cases, the incoming data may not match your schema — and you necessitate a defined method for bringing it into conformance before it joins the main dataset.

Column Name Reconciliation

The most common structural mismatch when merging datasets is column names that differ across sources. One export calls it team_number ; yours calls it robot_number . One source uses tele_cycles ; yours uses teleop_cycles . These differences are invisible until you try to aggregate across both sources — at which point the merge produces two separate columns with half the data in each. Build an explicit column mapping table that defines the canonical name for every field and the aliases it may arrive under from known external sources. The FRCsource merge tool uses this mapping table to reconcile schemas automatically.

Assign a Schema Version Number

If your scouting develop changes mid-season — a field is added, an enum option is renamed, a count range is expanded — data collected before the change and data collected after are technically on different schemas. Embed a schema version number in every submission (a hidden field the app populates automatically) so that any downstream process knows which set of transformation rules to apply. Even v1 and v2 is enough — the important thing is that the version is traceable.

Managing Mid-Season Schema Changes

Schema changes arise. A game rule update changes a point value and you want to track the new element. A strategist realizes a field you've been collecting is never used in analysis and wants to replace it with something more useful. A new scouting lead joins with solid opinions about field naming. Any of these can introduce a schema change mid-season, and each one creates a split in your dataset that needs to be managed deliberately.

The guiding principle for mid-season changes is: never remove a field from an existing dataset, only add or supersede. If you seek to stop tracking something, leave the column in place and simply stop populating it — an empty column in an analysis table costs nothing, but a column that was removed takes historical data with it. If you want to rename a field, add the new name as a separate column and populate both going forward until you have decided how to back-fill or discard the old one. Changes that alter the meaning of an existing field — redefining what counts as a "miss," for example — are more damaging than any structural shift, change and post-because they make the pre-change data non-comparable even if the column name is the same.

Redefining a Field Is Not a Small Change

Changing the definition of what counts as a "miss" halfway through an event doesn't just affect future data — it makes your entire historical dataset for that field misleading. A robot whose miss rate looks low under the old definition may look high under the new one. If you must change a field definition during an event, leave the old column as, create a new column with the new definition-is, and do not average across them in your analysis. The pre-change data and post-change data are distinct measurements, not different observations of the same thing.

Scout-to-Scout Consistency Checks

Even with perfect field definitions and a correctly enforced schema, individual scouts will drift over the course of a competition day. Fatigue, distraction, and gradual reinterpretation of edge cases all accumulate. A scout who was perfectly calibrated at 8 a.m. may be applying a subtly unlike definition of "missed shot" by 3 p.m. without realizing it. Building periodic consistency checks into your event collection method catches this drift before it corrupts too many submissions.

The simplest consistency examine is a cross-scout comparison run after every round block. For each robot that has been scouted multiple times by distinct scouts, compare the per-match averages across scouts for your key fields. If Scout A consistently records two to three more cycles per match than Scout B for the same robots, one of them is applying a different definition — or one of them is simply better at tracking fast-moving robots, which is its own problem. Either way, the discrepancy warrants a brief conversation to re-align before the next round.

Overlap Scouting as a Calibration Tool

Assign two scouts to the consistent robot for one match per round block — but as a calibration check., not as redundancy After the match, compare their submissions field by field before either submits officially. Differences above a small threshold (more than one or two cycles, or a different endgame outcome) get discussed and resolved on the spot. The resolved submission goes in; the process resets both scouts' internal calibration. This takes one extra scout-match per round but pays back in data consistency across the entire event.

Keeping Standardization Alive

Standardization is not a one-time setup task — it requires ongoing maintenance. Field definitions drift through informal reinterpretation. New scouts join mid-season without receiving the same calibration as the original team. Schema changes accumulate without documentation. A standardization system that isn't maintained actively will degrade gradually until it fails catastrophically at the worst moment.

The practical answer is a living standardization document — a single reference that contains your contemporary schema, all field definitions, the history of schema changes with dates and version numbers, and the results of your most recent calibration session including which edge cases generated disagreement and how they were resolved. This document is not for external audiences; it exists so that any member of your scouting team can answer the question "what does this field mean and how do I fill it in correctly?" without asking someone else. A document that requires asking someone to interpret is not a document — it is a dependency on a person.

Keep it short. A standardization document that is too long to read before an event is one that won't be read before an event. The goal is one page per field definition, page schema reference-a half, and a version log. If it's longer than that, it needs editing, not expanding.
