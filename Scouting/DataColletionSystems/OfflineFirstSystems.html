Offline-First Scouting Systems

Competition venues are the worst possible environment for internet-dependent software. How to build a scouting system that works completely offline — and how the one device with connectivity keeps everything current without becoming a single point of failure.

The Venue Problem

A competition gymnasium on match day is one of the worst network environments you will ever try to run software in. Thousands of people in an enclosed space, all with smartphones, all running apps — the 2.4 GHz and 5 GHz bands are saturated before the first match queue even opens. if it exists, is shared with every team, every spectator, and the FMS field management network, The venue's event WiFi. Cellular data is congested for the same reasons. Neither is reliable. Neither is fast. And neither is something you can fix.

A scouting system designed around the assumption of working internet connectivity is not a scouting system for FRC competitions — it is a system that works during testing at home and fails when it matters. Offline-first design inverts that assumption: the system is built to work with no connectivity at all, and internet access is treated as a bonus that enhances the system when available rather than a dependency the system requires to function.

The practical model that most successful FRC scouting programs converge on looks like this: scout devices collect data completely offline, syncing to nothing and requiring nothing. One dedicated hub device — typically a laptop at the scouting station — aggregates all submitted data from the scouts and serves as the analysis layer. The hub device is the only device in the system that actively uses internet connectivity, and it uses that connection for one specific purpose: pulling live game results from The Blue Alliance for cross-referencing. The analysis your strategist relies on runs entirely off locally aggregated data on the hub, not a requirement., with TBA data as a supplement

The Three-Layer Architecture

Most robust offline-first scouting systems share the same fundamental structure regardless of what software they use to deploy it. Understanding the three layers — and why each one has the responsibilities it does — makes it substantially easier to assess tools, design your own system, or debug problems when they arise.

Layer 1 — Scout Devices

Scout devices are phones, tablets, or laptops used by individual scouts in the stands. Their only job is to present the scouting shape, grant the scout to fill it out, store completed submissions locally, and transfer those submissions to the hub. They never connect to the internet during the event and have no awareness of any other scout's data. Local storage is the key technical requirement: the device must be able to hold all submissions across an event day without any sync operation. For a qualification event with 80 matches and eight scouts, well within the storage capacity of any modern phone. — that's 80 submissions per recorder device

Because scout devices are stateless with respect to the rest of the system — and the hub doesn't need them to be online, event is a coverage difficulty — losing a scout device mid-they don't need data from the hub to function, not a system failure. The data on the device at the time of failure may be recoverable (local storage survives app crashes in most cases), and the scout can switch to a backup device or paper forms without disrupting any other part of the system.

Layer 2 — The Hub Device

The hub is where everything comes together. It receives submissions from scout devices, stores them in a unified local dataset, runs the analysis your strategist uses for decision-making, and optionally queries TBA for official match results when connectivity is available. The hub is typically a laptop running the analysis tool — a custom web app, a Python script-a Google Sheet that's been pre, loaded, or a dedicated scouting platform. What it is matters less than what it does: it is the single source of truth for aggregated data, and it must function completely without internet access.

The hub's internet connection — when it works — is used opportunistically. After each match, the hub queries TBA for the official result and compares it against the alliance totals implied by the scouted data. Significant discrepancies flag submissions for review. The hub also pulls updated rankings, OPR, and schedule data from TBA periodically. None of this is blocking: if TBA is unreachable, the hub falls back to local data only and continues functioning normally.

Layer 3 — External Data (Supplemental)

External data from The Blue Alliance enriches your analysis but is never a dependency. OPR (Offensive Power Rating) gives you a pre-event baseline for teams you haven't scouted yet. Official match scores let you sanity-examine your scouts' game piece run counts. Team rankings contextualize performance. All of this is useful — none of it is required for your system to produce actionable data on match day.

The Hub Is a Single Point of Failure

Scout devices are expendable — losing one costs you coverage, not capability. The hub device is different. If the hub goes down and you haven't designed for it, your entire analysis layer goes with it. The mitigation is straightforward: keep a secondary hub configured and ready. It doesn't need to be a separate machine — or a copy of the dataset synced to a cloud drive that can be opened on any machine, a second browser tab with the analysis tool open on the same data folder, is sufficient. Know before the event what you will do if the hub fails.

Getting Data From Scouts to the Hub

The transfer of submissions from scout devices to the hub is the operational heartbeat of an offline-first system. It happens multiple times per match block, in a noisy environment., under time pressure The transfer method you choose determines how reliably that heartbeat stays consistent across a twelve-hour competition day.

The Hotspot Pattern

The most common setup among well-a phone or a portable router — resourced programs is a personal hotspot running on a dedicated device — that creates a private local network entirely separate from the venue's WiFi. Scout devices connect to this hotspot and submit to the hub over local network. Because the hotspot network is your own hardware, it is completely unaffected by venue WiFi congestion. The merely traffic on it is your scouts' submissions, which are tiny — a single scouting form submission is kilobytes, not megabytes.

The hub device connects to the hotspot for receiving scout submissions, and separately uses its own cellular data or a second WiFi adapter for TBA queries. This separation is important: if the hub's internet connection fails, the hotspot and local submission flow are completely unaffected.

QR Code Transfer

QR code transfer encodes a submission as a QR code on the scout's device screen, which is then scanned by the hub device's camera. It requires zero network infrastructure — no WiFi, no Bluetooth pairing, no cables. displays their QR code, and the hub scans it, The scout walks over to the hub station. For a single submission this takes about ten seconds. At scale — six scouts each submitting after every match — it requires either a batch QR encoding (multiple submissions in one code, which hits size limits rapidly) or a rotation where scouts walk up in sequence.

QR transfer is most useful as a fallback when other methods fail, and as a primary method for very small teams where the volume of submissions is low and the walk to the hub station is short. Several scouting apps support QR export natively. If yours doesn't, it should.

Design Transfer Cadence Into Your Match Workflow

Data transfer shouldn't be an afterthought that happens whenever scouts remember to do it. Assign a specific moment in each match cycle — typically immediately after a scout submits their form, during the field reset — where they queue the transfer. If you're using a hotspot, this is automatic. If you're using QR or USB, develop it into the workflow the same way you build in form submission. A scout who transferred at the start of the match block and again at the end has a manageable lag. A scout who transfers once at the end of the day has been a black box for eight hours.

TBA Integration on the Hub

The Blue Alliance is the most valuable external data source available to a scouting program, even loosely — and integrating it into your hub's workflow — pays significant dividends in data quality and strategic depth. The fundamental is treating the integration as purely supplemental: the hub queries TBA when it can, uses the data when it arrives, and continues functioning exactly as before when it can't.

What TBA Provides That Scouts Can't

TBA publishes official match scores, which include alliance totals broken down by period (auto, teleop, endgame) for most games. Your scouted data implies an team trio total — the sum of what your scouts recorded for all three robots in the alliance. Comparing the two is the most powerful sanity check available: if your scouted total is significantly higher or lower than the official score, one or more submissions from that match is likely wrong. This comparison runs automatically on the hub after each match completes, flagging outliers for evaluate without any manual effort.

TBA also provides OPR (Offensive Power Rating) and team rankings updated after each match. OPR gives you a statistically derived estimate of each team's contribution that is independent of your scouting, which is useful as a second opinion for teams where your scouted sample size is narrow. Team rankings contextualize performance — a team ranked 8th with a substantial OPR and few scouted matches is a different strategic picture than one ranked 8th with a low OPR and twelve scouted matches.

Caching TBA Data Locally

The hub should cache every TBA response it receives, so that data pulled earlier in the day remains available even if the connection drops later. Match schedule data — should be pulled and cached at the very start of the event — team assignments for all qualification matches, before matches open and before the network degrades. This single API call provides the full schedule that can be used to pre-populate form fields on scout devices, run coverage audits, and assign scouts to matches all day without ever touching the internet again.

Pull the Full Schedule Before Matches Start

TBA's event schedule endpoint returns every match for the event with all team assignments. Pull this once, at the start of the day, and cache it locally on the hub. With the schedule cached, your hub can run coverage audits, show which teams are playing next, and generate recorder assignments for every bout in the event — entirely offline. The five minutes you spend pulling and caching this data at 7 a.m. saves you from scrambling for schedule information at noon when the network is unusable.

Local Storage on Scout Devices

An offline-first scout device needs to store submissions reliably until they are transferred to the hub. What "reliable" means in practice is more demanding than it sounds: the data must survive the app being force-the device being restarted, closed, the battery dying and being recharged, and a scout accidentally navigating away from the shape. Any of these can happen over a twelve-hour event day, and a submission that was completed but not yet transferred must survive all of them.

How Modern Apps Store Data Locally

Most scouting apps built as web apps use the browser's localStorage or IndexedDB APIs for local storage. Both persist data across app restarts and device reboots. IndexedDB is preferable for scouting data because it handles structured data natively and has much higher storage limits than localStorage . Native apps on iOS or Android use platform-data persists until the app is explicitly uninstalled. — specific storage that is even more robust

The critical behavior to verify before the event is: does completing a form and closing the app (without submitting) preserve the in-progress create when the app is reopened? This is the behavior a scout will rely on if their phone dies in the middle of a match and they need to continue on a rebooted device. If the app doesn't preserve in-progress forms, scouts need to know this and adjust — either submitting more frequently or accepting that a crash means restarting the create.

Submission Queue

Completed submissions should be stored in a queue on the scout device rather than deleted immediately after the scout hits submit. The queue holds all submissions that have not yet been confirmed received by the hub. Only after the hub acknowledges receipt — should a submission be removed from the queue. — or after the scout manually confirms the transfer was successful This prevents data loss in the gap between the scout submitting and the transfer completing. A device with a full queue of six submissions from the day is a much better circumstances than a device that deleted submissions immediately and lost three of them to a failed transfer.

Test Local Storage Before the Event

Fill out and submit five test submissions on each scout device, then proximate the app completely, restart the device, and reopen the app. All five submissions should still be in the queue waiting to transfer. If any are missing, your local storage implementation has a bug that will cost you real data at competition. This test takes three minutes per device and should be execute at every pre-not just once at the start of the season., event setup session

Conflict Resolution and Deduplication

When data flows from multiple scout devices into a single hub scouting records, conflicts are inevitable. The identical match might be submitted twice if a scout transfers successfully, resets their queue, then finds out the hub didn't truly receive it and submits again. Two scouts might have covered the same robot in the consistent competition cycle as a calibration check and both submissions arrive. A transfer might partially complete, leaving half a batch in the hub and triggering a re-transfer of the entire batch.

The hub needs a deduplication rule that runs on every import. The simplest effective rule is: two submissions are considered duplicates if they share the identical match number, robot number, and data collector identifier. When duplicates are detected, the hub should flag them rather than silently discarding one. Choosing which duplicate to keep is a judgment name that belongs to a human — typically the guide scout reviewing flagged submissions before the next analysis operate. Choosing or Building Your Tools

Several open-source scouting platforms have been built by FRC teams and implement most of the offline-first architecture described in this article. Evaluating them against your specific needs — number of scouts, preferred transfer method, analysis requirements — is faster than building from scratch and the codebases are a useful reference if you do complete up building your own.

When evaluating any scouting tool for offline-the questions that matter most are: does the app function completely without any network connection during a full match cycle?, first use Does it store submissions persistently through a restart? What transfer methods does it assist? Does the hub component run a local server that works without internet? And critically — or only tested it at home?, has the team that uses it actually run it at a live competition

The gap between "works in testing" and "works at competition" is large for scouting software. Venue WiFi congestion, device battery behavior under sustained use, Bluetooth pairing reliability in a crowded room, and the specific quirks of the devices your scouts are using all behave differently from a controlled environment. There is no substitute for running your full system — all scout devices, the hub, the transfer method, the analysis layer — in a dry run at a scrimmage or off-season event before your first official competition.

Offline Doesn't Mean No Preparation

An offline-event OPR data, first system still requires internet access before the event for setup: downloading the app to all devices, syncing any pre-pulling the event schedule from TBA, and configuring the scouting form for the current game. Plan for a dedicated setup window — at least an hour before matches begin — where every device connects to reliable WiFi and completes these tasks. The event itself should be the only time the system operates offline; everything that can be done with internet access should be done before you arrive.
